# Этап 17. Направленная проверка кандидатов N3 GTP-TEID — уровни доказательности

**Реализация:** `src/phase17_teid_bridge.py` (декодирование только приватных transient PCAP в исполняемой Open5GS лаборатории) и `src/phase17_audit.py` (перепроверка подписанных обезличенных результатов на отдельном GitHub runner).

## Ожидаемое отношение идентификаторов

В 5GC используется N3 GTP-U туннелирование между NG-RAN и UPF. Различные tunnel endpoint identifiers отображаются в двух плоскостях:
- N2/NGAP: `ngap.gTP_TEID` — 4-байтовое OCTET STRING в NGAP PDU Session Resource Setup Transport Layer Information;
- N4/PFCP: `pfcp.f_teid.teid` — F-TEID в PDR, условно наблюдаемый в Session Establishment Response (msg type **51**), потенциально относящийся к UL PDR/N3 termination;
- N4/PFCP: `pfcp.outer_hdr_creation.teid` — Outer Header Creation в FAR, условно наблюдаемый в Session Modification Request (msg type **52**), потенциально относящийся к DL gNB termination.

**Ограничение реализации:** выделение по типам сообщений 51/52 накладывает фильтр *на PFCP*, но текущий декодер пока **не удостоверяет**, что конкретный NGAP GTP-TEID взят именно из Setup Request Transfer либо Setup Response Transfer. Также не доказаны IP tunnel endpoints (для NGAP TransportLayerAddress и PFCP F-TEID/OuterHeader), направление N3, соответствие PDR/FAR и принадлежность одному SM Context. Поэтому цифровые пересечения — исключительно **числовые кандидаты на принадлежность N3-туннелю**, не даже полностью подтверждённые UL/DL пары. Поля с названием `direction_gated_*` означают фильтрацию по PFCP message type, а **не** завершённую directional identity attestation.

## Правило проверки (только в памяти отдельной UE-попытки)

1. NGAP GTP-TEID — 4 байта в hex; `0000002a`, `00:00:00:2a` → uint32 42. PFCP TEID — декодированный tshark UInt32, обычно десятичный `42`; необоснованное прямое сравнение текстовых строк запрещено.
2. Отбросить TEID=0, неверные длины/некорректные значения.
3. Разбить PFCP candidates по типу 51 (F-TEID) и 52 (Outer Header Creation).
4. Для данного числового совпадения требовать **единственного NGAP PDU контекста внутри одного окна** и **одного PFCP transaction context по PFCP seqno и peer направлениям**. Дублирующие кадры tcpdump -i any одного transaction context объединяются. При повторном TEID с разными PDU context / N4 transaction context — состояние `ambiguous`.
5. Вывести лишь количества кандидатов UL/DL, неоднозначностей, NGAP numeric cardinality, PFCP cardinality и общее число числовых совпадений. **Исходные TEID, SEID, NGAP ID, IP, seqno, HTTP2 paths, subscriber IDs запрещено отправлять в подписанные КИЕ.**
6. `cross_protocol_identity_join_proven=false` для **всех** строк без отдельного доверенного корреляционного моста SMF; даже однозначное число в одном UE-окне не является доказательством.

Наиболее важный отрицательный контроль: *численное совпадение NGAP/PFCP TEID*, даже с message type 51/52 и отсутствием внутри окон коллизий, может возникать у чужой NF/PDU (некорректное направление, reuse в другом endpoints/подсети). Нельзя объявлять это доказательством отсутствия злонамеренной подмены.

## Почему исследования 17 и 16 не дублируют друг друга

Этап 16 проверял только три независимых наблюдения в общем временном окне и показал 18 таких окон без доверенной связи ID. Этап 17 **реально извлекает и численно сравнивает** отдельные GTP-TEID из двух протоколов, проверяет ошибочные пересечения и публикует ограниченную метрику сопоставимости в конкретных лабораторных процедурах. Это даёт дополнительный *возможный* механизм корреляции, но не превращает данные в криптографическую аттестацию.

Для перехода к уровням доказанной сессионной идентичности требуется дополнительно декодировать NGAP message direction и TransportLayerAddress, PFCP IE nesting / PDR/FAR source interfaces, проверить двухсторонние endpoint пары, отсутствие неоднозначности **по всему интервалу жизни сессии**, а затем защищённо привязать N3 tunnel → конкретный SM Context, PDU Session ID, UE identity. В этой модели это объявлено **не выполненным**.

## Научная интерпретация

Шесть видов неверных выводов защищены автоматическими тестами: NGAP-byte-hex vs PFCP decimal, нулевые/невалидные значения, чужие message type, повторный PFCP контекст, повторный NGAP PDU context, изменение подписанного доказательного статуса. Независимая подпись данных в одном GitHub административном домене не делает наблюдение доверенным при компрометации самого lab host.

Никакая метрика TEID-overlap не является Recall/FPR обнаружения реальной атаки; штатный SMF N4 fault — только технический отрицательный контроль.
