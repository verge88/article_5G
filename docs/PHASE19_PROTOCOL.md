# Этап 19 — пререгистрация причинной диагностики UL и настоящих двух конкурентных UE

**Протокол зарегистрирован 12 октября 2026 до нового 5GC запуска.** Исходный результат: этап 18 на 27 реальных PDU, 18/18 numeric UL N3 GTP TEID candidates, **0/18 endpoint+role UL candidates** и 18/18 DL candidates. Источники достоверны только в рамках одного привилегированного лабораторного администратора; истинная UE↔SM Context↔PFCP SEID identity не установлена.

## 1. Реальное увеличение конкурентности

Три новых disposable GitHub-hosted Open5GS+UERANSIM labs. Каждый содержит **два одновременно запущенных UERANSIM UE-процесса в двух разных Docker контейнерах** с двумя отдельно provisioned тестовыми IMSI, одним gNB и одной Open5GS 5GC (SMF/UPF/AMF/NRF). У них разные адреса в изолированном Docker bridge и отдельные конфигурации. Один capture-window содержит **две реальные параллельные PDU-попытки**, а не два последовательных UE-процесса; результат регистрации/PDU считывается отдельно из логов каждого UE.

По три окна в каждой из трёх фаз: normal, n4_full_drop (контролируемое правило блокирует только исходящий SMF UDP/8805 в SMF namespace, обе NF должны оставаться RUNNING), recovery (правило снимается, PFCP восстанавливается). Всего **27 окон и 54 настоящие UE PDU-попытки**. Успех каждой отдельной UE не присваивается по названию фазы; условие успешности baseline/recovery проверяется на реальном UE логе.

## 2. Сценарий ложной временной атрибуции

В одном общем окне теперь две разные UE, обе могут иметь одинаковый локальный NAS PDU Session ID (=1). Даже совпадение времени, общего gNB, одинакового PDU Session ID и одновременных PFCP транзакций **не доказывает, какой PFCP SEID относится к какой UE**. Поэтому запрет на повышение numeric-only или endpoint-only кандидата до authenticated cross-protocol join сохраняется.

## 3. Диагностика разрыва UL candidate этапа 18

Исследовать структурное дерево реальных NGAP/PFCP IE в личной памяти анализатора с tshark -T pdml, не экспортируя сырые поля. В частности проверить, присутствуют ли вложенные NGAP PDUSessionResourceSetupRequestTransfer / ResponseTransfer, PFCP F-TEID, Outer Header Creation и корректные (TEID,IPv4) поля в одних IE-subtrees. Плоский вывод tshark -T fields с несколькими IP/TEID нельзя произвольно связывать по индексам.

Сравнить на тех же новых окнах три уровня:
1. Числовая корреляция GTP TEID (этап 17).
2. Endpoint+role по одиночным плоским NGAP/PFCP fields (этап 18).
3. Структурная PDML observability: контекстный путь IE, наличие однозначных пар полей внутри одного subtree и информация об альтернативной ориентации UL/DL, при сохранении **candidate-only status**.

При наличии двух UE в одном окне числа и кортежи TEID и IP **обязательно остаются скрыты**, публикуются только cardinality и ambiguity. Проверки слабых категорий (недостаточно полей, отсутствующая/неоднозначная вложенная IE, конфликт endpoint/role, повторные кортежи) должны возвращать "abstain" при недостатке данных.

## 4. Измерения, а не ожидаемые проценты

Пререгистрированы: для каждого реального окна 2 UE outcome (4 возможных сочетания), отдельные регистрации и фактические PDU успехи, показатели N2/Nsmf/N4, candidate UL/DL числовой и endpoint, наблюдаемая структура IE, число неоднозначностей и примеры отсутствующей передачи; реальные dropped N4 пакеты, проверенные counters; отдельные подписанные квитанции Ed25519 для совместного окна + unsigned per UE outcomes; отсутствие удостоверенного UE↔SM Context↔PFCP SEID join. Три лаборатории × 9 окон = 27 подписанных КИЕ; независимый compute runner проверяет 27 подписей и 27 replay rejection.

## 5. Честные ограничения

Два UERANSIM UE в одном GitHub network namespace/одной административной зоне — **настоящие конкурирующие лабораторные процедуры, но не промышленная нагрузка и не независимые NF-владельцы**. Подписанное КИЕ host-level packet capture не равно NF attestation. Наблюдение отдельных SMF/UPF logs и структуры PFCP не создаёт автоматически защищённый identity bridge.

Если второй UE не регистрируется либо PDU не устанавливается в baseline, весь опыт по двум UE **не считается успешным**; нельзя заменить его последовательным UE или синтетическими локальными строками и по-прежнему назвать multi-UE экспериментом.

Если PDML структурный декодер не найдёт нужных вложенных полей, это будет записано как отрицательная observability, а не искусственно доказанная связь. Даже полное совпадение IP/TEID в обоих направлениях не даёт session identity without authenticated SM Context mapping.

Стандартные поля: https://www.wireshark.org/docs/dfref/n/ngap.html и https://www.wireshark.org/docs/dfref/p/pfcp.html (3GPP TS 38.413, TS 29.244).
