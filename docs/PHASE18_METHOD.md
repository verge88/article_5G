# Формализация этапа 18: удостоверяемые границы контроля N3 endpoint

**Метод записан 12 октября 2026 до получения новых сетевых метрик.** Исполняемый декодер: src/phase18_endpoints.py. Пререгистрация: PHASE18_PROTOCOL.md.

## 1. Множества протокольных фактов в окне UE

Пусть g — одна конкретная UE PDU-попытка в лаборатории. Наблюдатель получает из временного PCAP:

- N_UL(g) = {(TEID, IPv4, PDU_ID, procedureCode): NGAP initiatingMessage_element с единственным GTP_TEID, TransportLayerAddressIPv4 и PDU_ID в одной декодированной строке}.
- N_DL(g) — аналогичное множество из NGAP successfulOutcome_element.
- P_UL(g) = {(TEID, IPv4, PFCP transaction): F-TEID в PFCP Session Establishment Response (тип 51), одна F-TEID и одна IPv4 в данном декодированном сообщении}.
- P_DL(g) = {(TEID, IPv4, PFCP transaction): Outer Header Creation в PFCP Session Modification Request (тип 52), одна TEID и одна IPv4 в данном сообщении}.

Обозначения UL/DL относятся к предполагаемому направлению N3 из этих типов сообщений. NGAP ASN.1 вложенность в PDU Session Resource Setup Transfer, PFCP IE nesting внутри конкретного PDR/FAR и криптографический источник распределения туннелей пока **не подтверждены**. Это кандидат на совпадение endpoint, а не объявленная идентичность.

## 2. Два конкурирующих контроллера

**Numeric-only** (эталон этапа 17 на той же новой выборке): одинаковый 32-битный TEID в NGAP и PFCP type 51 / type 52, один NGAP PDU context и один PFCP transaction context. В сравнении нет IPv4 и роли внешнего сообщения NGAP.

**Endpoint-role** (новое уточнение): совпадение строго по (TEID, IPv4 endpoint) между N_UL/P_UL или между N_DL/P_DL. Для совпадающего кортежа требуется по одному локальному NGAP и PFCP контексту. Числовые значения нормализуются, IP-адреса синтаксически проверяются как IPv4, значения 0.0.0.0, multicast и loopback запрещены. Ни один результат Endpoint-role не может превышать Numeric-only по соответствующему направлению — нарушение приводит к ошибке проверки.

Функционально результат в каждом направлении:
- candidate: одно наблюдаемое совпадение с уникальными по этому окну локальными контекстами;
- abstain_ambiguous: неодинаковые PDU/PFCP contexts для того же endpoint tuple;
- abstain_missing: нет однозначного декодирования IP/TEID/NGAP role или полей несколько;
- not_correlated: доступные, но несовпадающие полные кортежи.

Последние два состояния в подписанных агрегатах оцениваются отдельно по counts observability, а не превращаются в доказательство отсутствия пакета в физической сети. Публикуются только counts; исходные IP, TEID, PDU_ID, SEID, packet capture и subscriber data не экспортируются.

## 3. Реальное вмешательство и проверка доверия

Три новых одноразовых Open5GS+UERANSIM 5GC, 27 настоящих PDU: normal 9, SMF N4 UDP8805 egress drop 9, recovery 9. Все контейнеры SMF/UPF работают, состояние регистрации SMF контролируется отдельно. Лабораторный iptables counter подтверждает, что пакеты отбрасывались, но не является NF-signed message или доверенным промышленным источником.

Ed25519 nonce-locked квитанция удостоверяет подпись лабораторного подписывающего процесса, не происхождение сообщения от самостоятельной NF. Независимый GitHub-hosted аудитор может подтвердить целостность и replay-protection, но его администратор тот же владелец репозитория.

## 4. Три уровня причинного утверждения

1. Same-window co-observation: UE PDU, NGAP, PFCP, HTTP/2 в одном времени.
2. Endpoint candidate: одно числовое TEID + IPv4 и предполагаемая роль N2/N4 соответствуют; не доказаны конкретный SM Context, PFCP SEID/вложенный PDR/FAR, межузловое криптографическое доверие.
3. Session identity proven: защищённый независимый мост NAS UE/PDU ID → Nsmf SM Context → PFCP SEID/правила → N3 endpoints; отсутствует в данном эксперименте.

При отсутствии удостоверенного моста любое утверждение из категории 3 запрещено. Условная наблюдаемая согласованность первого/второго уровня **не означает** ни отсутствие, ни присутствие скрытой компрометации NF.

## 5. Область применимости

Синтетические unit-тесты моделируют коллизии разных UE/PDU, несовпадающие IPv4 и повторный TEID. Никаких реальных конкурентных двух UE этап 18 не включает. Различная процедура NGAP (например Initial Context Setup vs PDU Session Resource Setup) может отображать поля PDU context в разных вложенных IE: декодер fail-closed, не сопоставляет многозначные плоские Wireshark поля по произвольному индексу.

**Критерий честного отрицательного результата:** даже если новый строгий Endpoint-role контроллер выдаст 0 candidates на реальном стенде, нельзя искусственно превращать теоретические совпадения Numeric-only в endpoint proof. Тогда этап фиксирует низкую наблюдаемость вложенных ASN.1/PFCP IE как фактическое препятствие для метода и выявляет необходимость структурного декодера с полным IE ancestry.
