# Этап 6 — сопоставление реальных PDU-сессий с HTTP/2 Nsmf_PDUSession

## Цель

Проверить наличие устойчивой временной связи между исходом отдельной попытки PDU-сессии в UERANSIM и фактически зарегистрированными запросами/ответами \`Nsmf_PDUSession\` в сервисно-ориентированном ядре Open5GS.

**Важно:** временное сопоставление **не** равно доказанной корреляции по сквозному идентификатору одной 3GPP-процедуры. HTTP/2 stream ID относится только к отдельному TCP-соединению и не является идентификатором UE или PDU-сессии.

## Методика

1. GitHub Actions изолированно поднимает реальные NRF/AMF/SMF/UPF, прочие необходимые NF, UERANSIM gNB/UE и тестового абонента. Используется зафиксированный коммит развёртывания 1f3bcf73f926b5b7526ef3c41cd2b839c2b17ac3.
2. На лабораторном узле кратковременно записывается pcap с TCP-портом 7777 (SBI HTTP/2). Он **не публикуется** и удаляется при завершении workflow.
3. Запускаются минимум по 6 попыток с SMF в состоянии normal, fail-stop и recovery. Контрольный аварийный останов разрешён только при наличии переменной ALLOW_LAB_ONLY_SMF_FAILURE=yes в изолированной лаборатории.
4. Для каждой попытки фиксируются начало и завершение интервала по UTC (время общего хоста), исход PDU по UERANSIM, регистрация UE, состояние SMF по Docker, регистрация SMF в NRF и агрегированные признаки AMF/SMF.
5. Tshark декодирует из живого pcap только метаданные HTTP/2: time_epoch, TCP conversation ID, HTTP/2 stream ID, имя семейства API, метод и статус ответа. Сырые пути, адреса, абонентские идентификаторы, содержимое запросов и токены доступа **не сохраняются** в публикуемом артефакте.
6. Повторные копии одного логического запроса дедуплицируются по TCP conversation + HTTP/2 stream ID; его ответ ищется по тому же ключу и временной последовательности.
7. Запросы Nsmf_PDUSession связываются с UE-попытками по непересекающимся временным окнам; подсчитываются уникальные запросы, сопоставленные ответы, HTTP-статусы и временные интервалы. Отдельно учитываются события вне окон.

## Защитные проверки достоверности

- Настоящая успешная сессия должна быть подтверждена UERANSIM в нормальном и восстановленном режимах.
- При остановленном SMF никакая попытка не должна завершаться успешной PDU-сессией.
- В нормальном и восстановленном режимах должны присутствовать реальные Nsmf HTTP/2-запросы, отнесённые по времени хотя бы к одной попытке.
- Пересекающиеся временные окна отвергаются: такие данные не позволяют однозначного временного сопоставления.
- HTTP/2-запросы и ответы не следует отождествлять с количеством PDU-сессий: на одну процедуру может приходиться более одного HTTP/2-запроса.
- Суммы запросов и HTTP-статусов могут зависеть от повторных операций SCP/AMF, модели непрямой коммуникации и характера захвата на Docker-host.

## Что НЕ доказывается

- Сквозное соответствие конкретной UE NAS-процедуры и отдельного Nsmf потока на уровне полноценного correlation ID.
- Целевая скрытая компрометация SMF и фальсификация его внутреннего состояния.
- Устойчивость к византийской компрометации ведущего контрольного узла.
- Корректность сетевого поведения оператора связи.
- Систематическая оценка ML Recall/FPR на реальных сценариях атак.

**План для более строгого этапа:** создавать защищённые идентификаторы контрольной операции в независимом внешнем агенте и проверять доступность корреляции через разрешённые поля/средства трассировки 3GPP; не вводить произвольные «сигнальные КИЕ» в SBI API без соответствия стандарту.
