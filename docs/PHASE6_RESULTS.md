# Этап 6 — реальная причинно-временная связь PDU-сессий и HTTP/2 Nsmf

**GitHub Actions:** https://github.com/verge88/article_5G/actions/runs/38138854662  
**Первичный артефакт:** phase6-real-temporal-nsmf-correlation (реальные интервалы UE, таблица HTTP/2-потоков по фазам, JSON-отчёты, версии контейнерных образов и кода).  
**Стандартная основа:** 3GPP TS 29.502 (Nsmf_PDUSession), TS 29.500 (HTTP/2 SBI).

## Постановка

На настоящем стенде Open5GS и UERANSIM проверялась возможность сопоставить отдельные попытки установления PDU-сессии с наблюдаемыми сервисными запросами и ответами между NF.

Контролируемое вмешательство: **остановка процесса SMF**. Это испытание доступности, **не кибератака и не скрытая компрометация**.

## Эксперимент

- 6 попыток при работе SMF, 6 при остановке, 6 после восстановления.
- Результат UE извлекается из реальных журналов UERANSIM.
- Данные о состоянии SMF поступают независимо от Docker.
- Кратковременный пакетный захват HTTP/2 на лабораторном узле анализируется tshark. Первичный pcap остаётся на runner и удаляется по окончании эксперимента.
- В каждом потоке HTTP/2 ответ соотносится с запросом по паре TCP conversation ID + stream ID; запросы Nsmf относятся к попыткам UE по **непересекающимся UTC-окнам**.
- В артефакт сохраняются только агрегированные характеристики, семейство протокольной операции, HTTP-статусы, относительное время и информация об исходе PDU. Исходные URL, адреса, содержимое сообщений и абонентские идентификаторы не публикуются.

**ВНИМАНИЕ:** это привязка по времени и по HTTP/2-потоку, а не сквозная идентификация процедуры 3GPP. Один вызов API, логический HTTP/2-поток и одна PDU-сессия не эквивалентны.

## Подтверждённые результаты

| Показатель | Нормальная работа | SMF остановлен | После восстановления |
|---|---:|---:|---:|
| ПДУ-сессии, успешно завершённые UE | 6/6 | 0/6 | 6/6 |
| UE успешно зарегистрированы | 6/6 | 5/6 | 6/6 |
| SMF активен (Docker) | 6/6 | 0/6 | 6/6 |
| Уникальные HTTP/2-потоки с Nsmf-запросами | 34 | 145 | 34 |
| Потоки с найденным HTTP-ответом | 28 | 144 | 34 |
| Ответы HTTP 2xx | 28 | 72 | 34 |
| Ответы HTTP 4xx | 0 | 0 | 0 |
| Ответы HTTP 5xx | 0 | 72 | 0 |

В общей сложности 18 настоящих попыток PDU, 213 логических HTTP/2-потоков с Nsmf-запросом, 206 сопоставленных ответов (**96,71 %**). Все 213 обнаруженных потоков соотнесены с одним из непересекающихся временных окон; запросов Nsmf вне окон не зафиксировано.

При остановке SMF объём потоков с Nsmf-запросами составил 145/34 ≈ **4,26 раза** от нормальной фазы. Наличие 72 ответов 2xx одновременно с 72 ответами 5xx при **нуле успешных PDU-сессий** подчёркивает, что успешность одного API-вызова не равна успешности сетевой процедуры.

Для **пяти из шести** испытаний фазы остановки SMF зарегистрированы HTTP 5xx; в одной попытке UE не зарегистрировался и таких ответов не наблюдалось. Это пока только описание, не оценка эффективности универсального детектора.

## Проблемы наблюдаемости и источники ошибки

1. Три фазы проведены в одном развёртывании с одним моделируемым UE; шестёрки попыток одной фазы не являются независимыми операторами или разными версиями 5GC.
2. Временные окна включают контейнерное создание/выключение UE; при нескольких одновременных UE их недостаточно для однозначного связывания действий.
3. Идентификатор HTTP/2 stream уникален лишь внутри одного TCP-соединения. Он не является идентификатором UE или 3GPP PDU-сессии.
4. Захват с хостового интерфейса any может дублировать кадры; программная дедупликация не исключает всех неоднозначностей прокси и сетевых переподключений.
5. Пара HTTP/2 запрос–ответ связывается по TCP stream/HTTP2 stream ID, но связь с отдельной NAS-сессией подтверждена только временем.
6. Рост количества HTTP-запросов при отказе ещё не доказывает конкретную причину, например повторные попытки или поведение SCP. Для этого нужно декодировать семантику и причинно-временные зависимости сервисных вызовов.
7. Вмешательство — штатный fail-stop, не злоумышленное изменение результата при нормальном HTTP/2.
8. На этих 18 записях **не следует заявлять достоверно измеренные показатели Recall/FPR для выявления скрытых компрометаций**.

## Принципиальное уточнение по научной новизне

3GPP TS 29.500 V18.9.0 уже определяет *опциональный* заголовок 3gpp-Sbi-Correlation-Info (разделы 5.2.3.3.4, 6.13.2), а также 3gpp-Sbi-NF-Peer-Info (раздел 6.13.3).

Источник: https://www.etsi.org/deliver/etsi_ts/129500_129599/129500/18.09.00_60/ts_129500v180900p.pdf

Поэтому сама идея корреляции не является новым научным результатом. В данном эксперименте наличие этих заголовков в Open5GS **не исследовалось**. Следует отдельно проверить их поддержку и принятые ограничения приватности.

Более узкая гипотеза для будущей статьи: верификация причинной согласованности исхода 5G-процедуры по независимым КИЕ и SBI-событиям в пределах доверенных временных границ, с результатом «неопределено», если отсутствует достаточно независимых свидетельств.

Для её доказательства потребуются настоящий контроль семантического результата процедуры, контрольные агенты в разных доменах доверия и моделируемая злоумышленная фальсификация состояния при функционирующей NF, а не только fail-stop.
