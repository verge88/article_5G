## 1. Научная задача

Этап 17 обнаружил реальные числовые совпадения 32-битного GTP-TEID между N2/NGAP и N4/PFCP в 18 успешных индивидуальных временных окнах UE. Но **равенство номера TEID не гарантирует, что совпадает N3 GTP-U endpoint**, поскольку TEID локален относительно конечной точки и направления.

Новый эксперимент сравнивает кандидаты по тройке:

- **UL/UPF:** NGAP initiatingMessage с однозначным ngap.gTP_TEID, ngap.TransportLayerAddressIPv4 и ngap.pDUSessionID; PFCP Session Establishment Response type 51: pfcp.f_teid.teid и pfcp.f_teid.ipv4_addr.
- **DL/gNB:** NGAP successfulOutcome c соответствующим TEID и TransportLayerAddressIPv4; PFCP Session Modification Request type 52: pfcp.outer_hdr_creation.teid и pfcp.outer_hdr_creation.ipv4.

Сравнение происходит **по нормализованным числам и адресам только в приватной памяти**. Исходные PDU IDs, NGAP/PFCP адреса, TEID, SEID, HTTP headers/body, SUPI/IMSI и PCAP не экспортируются. Подписываются только агрегированные количества и признаки достоверности. Плоская строка tshark с несколькими IP/TEID значениями не связывается произвольным индексом и исключается из строгой проверки.

**Важное ограничение:** роль initiating/successfulOutcome — внешний NGAP уровень, а PFCP IE извлекается фильтрацией по type 51/52. Вложенная структура NGAP Transfer и PDR/FAR IE (точное назначение TEID) **не удостоверена**. Поэтому даже успешное совпадение IP+TEID+роли здесь остаётся *кандидатом связи туннелей*, не доказанной принадлежностью PDU ↔ PFCP SEID и не защищённым подтверждением NF.

## 2. Реальный эксперимент

Три новые disposable Linux GitHub runner, каждый с отдельной реальной Open5GS 5GC + UERANSIM gNB/UE. По три настоящих PDU-попытки в норме, при полном блокировании только исходящего SMF UDP/8805 PFCP/N4, и после снятия правила. SMF и UPF **не останавливались**. Реальный PDU outcome получен из UERANSIM; N4 drop от kernel firewall в SMF namespace — отдельно помеченный привилегированный лабораторный oracle.

| Состояние | Реальные попытки UE | Успешные PDU | PFCP Req/Resp наблюдались | Числовые UL-кандидаты | Числовые DL-кандидаты | Строгие UL IP+role кандидаты | Строгие DL IP+role кандидаты | Реальные N4 drops |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Норма | 9 | **9** | 9 | 9 | 9 | **0** | **9** | 0 |
| SMF N4 drop | 9 | **0** | 0 | 0 | 0 | 0 | 0 | **191** |
| После восстановления | 9 | **9** | 9 | 9 | 9 | **0** | **9** | 0 |
| **Итого** | **27** | **18** | **18** | **18** | **18** | **0** | **18** | **191** |

На каждом отдельном стенде было 3/3, 0/3, 3/3 успешных PDU. N4 packet drops на трёх машинах: **67, 61, 63**, всего 191.

**Главный новый отрицательный результат:** 36 числовых N3 TEID-кандидатов из этих же новых окон сократились до **18** при добавлении IPv4 адреса и строгой роли. Все 18 DL-кандидатов прошли проверку; **ни один из 18 UL-кандидатов не прошёл**. Это не означает, что реальная UL GTP-U связь физически нарушена: все 18 UE успешно установили PDU. Новая проверка выявила **пробел доказательности** при выбранных полях/семантике декодера; причинный вывод о неверной маршрутизации UL из этого не следует.

Установленные факты исходной декодируемости: при норме и восстановлении суммарно **36 NGAP кадров с полем TEID**, **36 NGAP кадров с ровно одним декодированным IPv4** и **36 PFCP кадров с одним IPv4**. Таким образом отрицательное UL-соответствие возникло не от полного отсутствия IP-полей в capture. Возможные альтернативы: разная интерпретация внешнего NGAP направления, фактически различающиеся endpoint IP при равном TEID, или недостаточная вложенная привязка ASN.1/PFCP IE. **В текущих обезличенных сводках эти причины не различаются; нельзя называть одну доказанной.**

Внутри 27 временных окон проверяющий не обнаружил неоднозначных *уже совпавших* endpoint tuples, но **при одной UE на окно** это не доказывает отсутствие коллизий TEID в конкурентной сети. Два UE/две разные конечные точки, злонамеренная подмена и ошибочные совпадения моделировались только unit tests, а не реальным конкурентным multi-UE экспериментом.

## 3. Методическое сравнение

**Numeric-only:** совпадает числовой 32-bit TEID при ограничениях на тип PFCP (51 или 52), без проверки IPv4 и внешнего NGAP role. Дал 18 UL + 18 DL кандидатов.

**Endpoint+role:** требует полные и неколлидирующие (TEID,IPv4) и подходящую роль NGAP. Дал **0 UL + 18 DL** кандидатов. Число endpoint candidates не может превышать соответствующее число numeric-only; отдельный CI verifier перепроверил это ограничение.

**Authenticated identity:** отсутствие независимого защищённого отображения NGAP PDU ID ↔ SM Context ↔ PFCP SEID означает **0 подтверждённых сессионных identity joins**. Это **не 18 реальных неверных связей**, а 18 DL-кадровых кандидатов, которые не имеют сессионного proof.

Такое различение предотвращает систематическое завышение полноты и уверенности: при неравных типах доверия в КИЕ нельзя отождествлять числовое совпадение и удостоверенную идентичность.

## 4. Независимая проверка данных и подписи

В отдельном успешно выполненном GitHub Actions job загружены **оригинальные, неизменённые артефакты трёх реальных стендов**, заново проверены:
- 27/27 подписанных Ed25519 KIE, nonce, порядок последовательностей, свежесть, source/service;
- 27/27 повторных предъявлений отклонены;
- совпадение исходных trial rows с собственной подписанной КИЕ, включая numeric candidates, endpoint-role matches, NGAP/PFCP observability и N4 drop counters;
- полные 27 UE outcomes, условия N4 intervention и восстановление;
- endpoint candidate counts не превышают numeric-only, и **cross_protocol_identity_join_proven=false** на всех 27 попытках.

Отдельный GitHub runner — лишь **независимая машина для вычисления**, а не независимый администратор NF и не cryptographic attestation корневого источника данных. Подпись удостоверяет неизменность утверждения лабораторного host-agent, не истинность самой NF при компрометации.

## 5. Достоверность и дальнейшая работа

Подтверждено: (a) строгий endpoint/role comparator реализован на настоящих NGAP+PFCP; (b) половина numeric-only candidates не сохраняется при усилении условий; (c) PDU outcome не может выводиться из условного UL negative; (d) обоснованный отказ в полном PDU/PFCP identity proof сохраняется.

**Не подтверждено:** реальная скрытая компрометация NF, защищённый session identity join, правильная PFCP PDR/FAR IE ancestry, подлинное администрирование свидетелей разными владельцами, реальный конкурентный multi-UE collision load, достаточная работа в операторском 5G Core.

Для получения строгого UL-доказательства необходим следующий узко сформулированный опыт: **сохранить приватный IE-tree контекст NGAP PDU Session Resource Setup Request Transfer / successful response и PFCP PDR/FAR вместе с UE↔UPF/gNB tunnel IPv4**, подтвердить направление не только внешним message outcome и добавить защищённый SM Context correlator. Затем предъявить **два разных реально provisioned UE** одновременно; сравнить ложную уникальность Numeric-only и endpoint+role при общих TEID/различных IP/SEID.

Ни нулевое UL endpoint match, ни 100% успешных PDU в штатных окнах **не являются FPR/Recall детектора реального злоумышленного NF**.
