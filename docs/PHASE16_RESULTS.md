## 1. Объект нового исследования

Предыдущая фаза 15 независимо подтвердила связь *внутри PFCP* — Request type 50 и Response type 51 можно сопоставлять по Sequence Number, обратным IP/UDP endpoint и времени. **Однако это не означает доказанную причинную связь между конкретным UE PDU Session ID и PFCP SEID.**

Шестнадцатый этап добавил настоящий совместный пассивный захват:
- **N2/NGAP** (SCTP/38412), поле `ngap.pDUSessionID`, сохраняется только факт и cardinality ID;
- **SBI/Nsmf** (TCP/7777), HTTP/2 logical request/response по паре `(tcp.stream, http2.streamid)`, сохраняются количество потоков и наблюдённые HTTP-классы;
- **N4/PFCP** (UDP/8805), PFCP sequence plus обратные UDP endpoints, а также cardinality nonzero PFCP header SEID.

Все значения SEID, PDU ID, stream ID, IP, абонентские данные, заголовки/тела сообщений остаются только в оперативной памяти анализа. Сырой PCAP создаётся на один UE trial во временном каталоге и удаляется. В GitHub публикуются обезличенные количества и подписанные Ed25519 КИЕ **агента лабораторного захвата**; не подписью самой SMF/UPF.

В трёх новых disposable 5GC каждый стенд провёл 9 настоящих попыток UE, всего **27**: 3 normal, 3 с контролируемым исходящим N4/PFCP UDP/8805 drop при работающих SMF и UPF, 3 recovery. Ни остановки NF, ни атаки/подмены NF не было. Сетевой Docker state и iptables — **привилегированные лабораторные свидетельства**, не независимые 3GPP доверительные домены.

### 2.1 Что действительно сообщает Nsmf/HTTP2

| Фаза | Nsmf HTTP2 logical request streams | Потоки с наблюдённым HTTP2 reply | Среди reply 2xx | Среди reply 5xx |
|---|---:|---:|---:|---:|
| normal | 48 | 33 | 33 | 0 |
| n4_full_drop | **52** | **6** | 0 | **6** |
| recovery | 48 | 30 | 30 | 0 |
| **Всего** | **148** | **69** | **63** | **6** |

Несмотря на отсутствие успешных PDU при N4 drop, Nsmf/SBI-запросы **не прекратились**. Их число даже больше в отказном режиме (52 против 48 нормальных, но фазы имеют различную фактическую длительность). Наблюдаемые ответы 5xx согласуются с неисправностью сервисного взаимодействия; отдельный HTTP2 2xx/5xx **не равняется конечному NAS/PDU outcome**.

**79 Nsmf request streams не имеют response *внутри измеренного PCAP*.** Нельзя интерпретировать их как доказанно безответные на уровне сети: ответ мог прийти после закрытия временного окна, быть потерян packet capture или некорректно декодирован.

### 2.2 Границы наблюдаемости NGAP и PFCP

В нормальном режиме и после восстановления в **18/18 успешных окнах** видимы NGAP PDU Session ID и PFCP Session Establishment парные запросы/ответы. В фазе N4-drop эти поля не были декодированы в 9/9 окнах, хотя Nsmf оставался наблюдаемым; при этом **196 реальных UDP/8805 пакетов** были отброшены Linux kernel в SMF network namespace.

Отсутствие NGAP PDU Session ID в PCAP — это **отсутствие наблюдения данного декодированного поля**, не доказательство, что ни одного NGAP сообщения в сети или UE NAS контекста не было. Вывод о непригодности PDU опирается отдельно на настоящий UERANSIM результат.

## 3. Почему три протокола не образуют автоматически одну идентичность

При нормальной работе и после восстановления **в 18 UE-окнах одновременно присутствовали**:
1. настоящий NGAP PDU Session ID;
2. настоящий HTTP/2 Nsmf_PDUSession request;
3. настоящий PFCP Session Establishment Request/Response с корректным sequence+reverse-peer matching.

Ни один стандартный наблюдаемый номер сам по себе не равен остальным: NGAP PDU ID является локальным session identifier, HTTP/2 stream ID — номером запроса в соединении, PFCP seqno — номером транзакции N4, а PFCP SEID — локальным session context NF.

**Проверяемый отрицательный контроль:** наивный алгоритм `все три сообщения видны в одном окне ⇒ NGAP PDU и PFCP сессия идентичны` выдал бы **18 необоснованно уверенных заключений**. Дисциплинированный контроллер возвращает `insufficient_identity_binding` для всех 27 окон, поскольку нет удостоверенного отношения:
`NGAP PDU Session ID → SM Context/Nsmf reference → PFCP SEID`.

**Это не означает, что все 18 совпадений ложные!** При одном тестовом UE и неперекрывающихся окнах весьма вероятно, что наблюдаемые транзакции связаны причинно. Но вероятная физическая связь **не равна доказанному межпротокольному отображению ID**, особенно при нескольких одновременных UE и недостоверном источнике телеметрии. Поэтому показатель 18 не следует превращать в FPR обнаружения кибератак или accuracy идентификации без внешней истины.

## 4. Доверие, криптография и аудиторская проверка

Каждый из трёх runner исполняет 9 настоящих UE-попыток, создаёт 9 подписанных Ed25519 обезличенных KIE с nonce, sequence, timestamp, trial-token и отдельным ключом, хранящимся только в `TemporaryDirectory`. Итог: 27 реальных КИЕ.

Отдельный GitHub job получает **оригинальные ZIP трёх лабораторий** и проверяет соответствие подписанных NGAP/Nsmf/PFCP метрик опубликованным строкам, все подписи, nonce, session tokens, последовательные номера и отказ в replay. Подробные подтверждённые значения публикуются в `verified_threeplane_summary.json` после завершения проверки.

Важное ограничение: подписание разных протоколов одним агентом захвата и проверка на другом GitHub runner, управляемом **тем же владельцем репозитория**, не создают независимых административных доменов и не аутентифицируют содержимое NF при злонамеренной компрометации.

## 5. Границы новизны

Подтверждён полезный методологический принцип: отделять **co-observation**, **within-protocol request-response proof** и **cryptographically/procedurally verified cross-plane identity**. Это не новая функция стандартов NGAP, PFCP или Wireshark; научная новизна будущего детектора скрытой компрометации остаётся недоказанной.

Следующий опыт должен по-настоящему связывать PDU ID с PFCP не только временем, а общим проверяемым коррелятором. Возможный кандидат: N3 GTP-TEID, присутствующий в NGAP transfer и некоторых PFCP IE (подтверждать направление и назначение туннеля); либо защищённый SMF-side диагностический bridge `PDU/SM Context ↔ PFCP SEID`. Он должен иметь независимый владельческий trust domain, проверку свежести и неоднозначности, и защищённый протокол для контролирующего агента.

**Настоящей атаки, скрытой компрометации NF или подмены данных NF этап 16 не воспроизводил.**
