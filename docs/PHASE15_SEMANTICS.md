# Формальная семантика PFCP-КИЕ на уровне наблюдённого UE-окна (этап 15)

**Документ методики, созданный до проверки новых результатов.** Код: \`src/phase15_pfcp_windows.py\`, \`src/phase15_live.py\`, \`src/phase15_audit.py\`.

## 1. Типы источников и доверие

В одном локальном испытании наблюдаются **три различных, но не административно независимых** источника:

- UE: UERANSIM outcome \`U_i ∈ {success, not-observed-success}\`. Второе означает, что успешное завершение не было обнаружено в заданный timeout, а не доказанный отрицательный NAS ответ.
- P: пассивный packet capture PFCP UDP/8805 на лабораторном host. Только в этом источнике можно наблюдать конкретные PFCP сообщения. Никакой защищённой подписи, исходящей от SMF/UPF, нет. Подпись принадлежит агенту захвата.
- NF: NFProfile в NRF и прослушивающий UDP 8805 сокет UPF. Это только *presence*, не завершённость процедуры.

Дополнительный \`D_i\`: число реально сброшенных исходящих SMF PFCP-пакетов, полученное из Linux \`iptables-save -c\` в privileged SMF network namespace. Это доверенное только относительно **одноразового лабораторного администратора** наблюдение; операционную независимость оно не обеспечивает.

## 2. Наблюдение внутри окна

Для каждой отдельно запущенной UE попытки \`i\` временный PCAP открывается перед запуском \`nr_ue\` и закрывается после окончания \`trial()\`. Анализатор читает локально кортеж \`(time, src IP, dst IP, src UDP, dst UDP, pfcp.msg_type, pfcp.seqno)\`, но публикует только агрегаты.

Сообщения \`REQ=50\` и \`RSP=51\` образуют наблюдаемую пару тогда и только тогда, когда:

1. Имеют одинаковый PFCP sequence number;
2. UDP/IP endpoints ответа противоположны endpoint'ам запроса;
3. Время ответа не предшествует запросу;
4. Оба сообщения увидены **в рамках одного UE capture window**;
5. Один наблюдаемый ответ не используется для нескольких запросов.

Эвристика слияния повторной видимости пакета на интерфейсе \`any\`: идентичный кортеж с интервалом ≤50 мс учитывается один раз. Поэтому цифры **не эквивалентны уникальным PFCP транзакциям**, и реальные retransmission могут ошибочно сливаться с копиями захвата.

На выходе: \`req_i\`, \`rsp_i\`, \`matched_i\`, \`unmatched_req_i\`, \`unmatched_rsp_i\`, \`min/max paired RTT\` и \`D_i\`. Исходные IP, seqno, SEID, SUPI/IMSI и PCAP запрещено отправлять в CI artifacts.

## 3. Трёхзначные суждения

**Подтверждённая локальная наблюдаемость (observed):** \`matched_i>0\` означает, что в capture window *действительно наблюдалось* хотя бы одно согласованное PFCP Request/Response взаимодействие. Это не достаточное доказательство, что оно принадлежит данной UE PDU; его могли вызвать иные процедуры или повторы.

**Доказанный лабораторный N4 impairment (lab-confirmed):** \`D_i>0\` означает, что локальный kernel firewall действительно отбросил PFCP egress пакеты **в окне**. Это сильно поддерживает причинный путь воздействия, но этот привилегированный свидетель не является NF-attested доказательством компрометации.

**Неопределённость (unknown):** \`req_i=0\`, \`rsp_i=0\`, непарные \`REQ\`, неполная/недоступная capture или успешная PDU без наблюдаемого match **не позволяют утверждать отсутствие PFCP в реальной сети**. Внешнее подтверждение полноты захвата отсутствует.

**Отказ конечного сервиса (UE observed failure):** \`U_i=0\` при работающих NF и зарегистрированной SMF ещё не доказывает ни конкретную причину, ни злонамеренную активность. Требуется дополнительный связывающий документ между PDU и PFCP на основе 3GPP Session/Nsmf reference и надёжных источников.

## 4. Невозможность строгого вывода по одному PFCP sequence number

PFCP sequence number принадлежит N4 транзакции, тогда как UE PDU Session ID и Nsmf SM Context являются объектами другой плоскости/протокола. Номер последовательности сам по себе **не является межпротокольным идентификатором процедуры UE**. Поэтому при совпадении в одном временном окне допустимо писать \`PFCP transaction co-observed during UE attempt\`, а **нельзя** писать \`this PFCP request proves that UE's PDU session established\`.

Отдельный наиболее важный дальнейший шаг — безопасная correlation chain через SMF: защищённый локальный источник соответствия PDU/SM Context ↔ PFCP SEID/transaction, плюс свидетели других доверительных доменов. Такая цепочка ещё не реализована.

## 5. Честные условия будущего научного вывода

- Никакая категория \`PDU failed\` не обозначает кибератаку.
- При реальной выборочной потере \`nth every 2\` измерять **настоящий успех UE**, не считать заранее «50 % PDU неуспехов».
- Следует показать долю успешных PDU без matched PFCP и долю неуспешных PDU с matched PFCP — обе группы важны для опровержения наивного бинарного контроля.
- Сопоставлять фиксированный endpoint-presence контроль и протокольно-временной контроль **без использования firewall drop counter в промышленной модели**, если он доступен только privileged lab.
- Даже если шаблон «PFCP пара отсутствует ↔ PDU неуспешна» покажет 100 % на 48 лабораторных попытках, это не оценка эффективности обнаружения скрытой компрометации NF или независимая статистическая валидация.
