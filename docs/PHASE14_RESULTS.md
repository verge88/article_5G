# Этап 14. Реальный разрыв PFCP/N4 при работающих SMF и UPF: контроль подписанными КИЕ

**Дата:** 11 октября 2026 года.
**Фактический эксперимент:** GitHub Actions [#38159871173](https://github.com/verge88/article_5G/actions/runs/38159871173), 3 отдельных одноразовых Open5GS + UERANSIM 5GC и отдельный верификационный job.
**Исполненный код:** коммит \`f9ef2645098ff6d06fc2502e46c17d8eeaa75d53\`.
**Внешний код лаборатории:** herlesupreeth/docker_open5gs commit \`1f3bcf73f926b5b7526ef3c41cd2b839c2b17ac3\`; actual image digests retained in each real-run artifact.
**Пререгистрированный до измерений протокол:** [PHASE14_PROTOCOL.md](PHASE14_PROTOCOL.md).

## 1. Сетевая постановка

В этом эксперименте ни SMF, ни UPF не останавливались. На эфемерной тестовой машине Linux-политика \`iptables\` была временно включена **в сетевом пространстве имён SMF**, ограничена цепочкой OUTPUT, протоколом UDP и **портом назначения 8805 (PFCP)**. Это блокировало исходящий N4/PFCP трафик SMF, не уничтожая саму сетевую функцию, её UDP listener у UPF или регистрацию SMF в NRF. Правило снималось в защищённой ветке \`finally\`; исходное сетевое пространство Docker уничтожалось после эксперимента.

В каждом из трёх новых GitHub runners выполнено 12 настоящих UERANSIM UE PDU-попыток:
- \`normal\`: четыре обычных установления PDU без N4 firewall;
- \`n4_pfcp_drop\`: четыре установления при блокировании **только исходящего PFCP SMF**;
- \`recovery\`: четыре установления после удаления правила и восстановления PFCP.

**Это контролируемая штатная лабораторная неисправность канала связи, не зловредная компрометация NF, не подмена подписанной телеметрии и не атака на реальную сеть.** Исход каждой PDU-попытки получен из UERANSIM, а не назначен по названию фазы.

## 2. Настоящие исходы UE и сохранённая видимая работоспособность NF

| Стенд | Штатные PDU | N4 заблокирован | После удаления правила | Счётчик реально отброшенных исходящих PFCP-пакетов |
|---|---:|---:|---:|---:|
| 11 | 4/4 | 0/4 | 4/4 | 83 |
| 22 | 4/4 | 0/4 | 4/4 | 88 |
| 33 | 4/4 | 0/4 | 4/4 | 82 |
| **Итого** | **12/12** | **0/12** | **12/12** | **253** |

Все три стенда независимо измерили:
- SMF Docker-running = true во всех трёх фазах;
- UPF Docker-running = true во всех трёх фазах;
- рабочий HTTP/2 Nnrf_NFDiscovery с **одним** зарегистрированным SMF в конце каждой фазы;
- доступный UPF network namespace и присутствующий PFCP UDP-порт 8805;
- невозможность установить UE PDU (0/12) в фазе N4 UDP drop;
- восстановленные реальные UE PDU (12/12) после удаления правила **без перезапуска SMF и UPF**.

Следовательно, положительная регистрация SMF и наличие открытого UDP/PFCP-сокета у UPF **не являются достаточным подтверждением работоспособности обмена N4 и полной PDU-процедуры**. Это особенно важно для иерархических контрольных информационных единиц: наличие NF не означает допустимого сервисного результата.

В то же время временная последовательность и целевое вмешательство дают **лабораторную интервенционную связь**, но не строгую всеобщую гарантию причинности при независимых конфигурациях, нагрузках и других реализациях 5G Core.

## 3. Пассивно декодированные настоящие PFCP сообщения

Реальный \`tcpdump\` слушал UDP 8805 на интерфейсе Linux \`any\`; \`tshark\` декодировал \`pfcp.msg_type\`. Только агрегированные **количества наблюдаемых PFCP-сообщений**, без IP, SEID, IMSI/SUPI, NAS или сырых пакетов, опубликованы в GitHub артефактах.

| Тип сообщения | Норма: суммарно 3 стенда | N4 egress drop: 3 стенда | Восстановление: 3 стенда |
|---|---:|---:|---:|
| Heartbeat Request | 28 | 18 | 24 |
| Heartbeat Response | 28 | **0** | 24 |
| Association Setup Request | 0 | **112** | 0 |
| Session Establishment Request | 24 | **0** | 24 |
| Session Establishment Response | 24 | **0** | 24 |
| Session Modification Request | 24 | 0 | 24 |
| Session Modification Response | 24 | 0 | 24 |
| Session Deletion Request | 18 | 0 | 18 |
| Session Deletion Response | 18 | 0 | 18 |
| **Все PFCP-сообщения** | **188** | **130** | **180** |

В фазе отказа получены 112 Association Setup Requests и 18 Heartbeat Requests, но **нет видимых ответных Heartbeat и Session Establishment сообщений**. Это важно: блокировка SMF OUTPUT не означает физического исчезновения всех PFCP датаграмм на сетевом интерфейсе — часть реальных попыток со стороны UPF всё ещё наблюдается.

Числа представляют **наблюдения PFCP кадров, а не уникальные PFCP-сессии или гарантированно связанные с конкретной PDU попыткой сообщения**. Захват на \`any\` может дублировать один физический пакет. При отсутствии кадров нельзя доказать отсутствие попытки или отсутствие ассоциации без других источников.

Отдельный Linux firewall counter документирует реальные пакеты, **сброшенные в сетевом пространстве имён SMF**: 83 + 88 + 82 = **253**. Это привилегированное свидетельство host runtime и не является подписанным самой 3GPP NF сообщением или защищённой междоменной телеметрией.

## 4. Подписанные контрольные информационные единицы

Каждый стенд создал три подписанных агрегированных КИЕ на каждую из трёх фаз:

1. NRF-свидетельство HTTP/2 Discovery SMF, полученное отдельным агентским процессом.
2. UPF-свидетельство наличия PFCP listening socket, полученное через privileged Docker namespace inspection.
3. Пассивное PFCP-свидетельство с количеством декодированных типов сообщений и числом реально отброшенных PFCP-пакетов, собранное на host lab.

Всего ожидается **27 цифровых квитанций Ed25519** с разными ключами трёх типов наблюдений, уникальными nonce, monotonic sequence и явным идентификатором сервиса. Проверка в отдельном runner должна подтвердить идентификатор каждого источника, подпись и отказ в повторной передаче. Обязательность подписи **не свидетельствует об истинности источника**, поскольку все агенты и ключи создаются в одном GitHub административном домене.

### Результат отдельной проверки

См. успешный отдельный job \`Separate runner verify signed PFCP traces and independent network outcomes\` в экспериментальном запуске. Итоговый архив \`phase14-independent-verified-PFCP\` содержит \`verified_pfcp_results.json\` и \`REPORT.md\`; числа подписей и повторы следует брать именно из завершённой проверки артефактов.

## 5. Что доказывает новый контроль, чего не доказывали этапы 12–13

Этапы 12–13 демонстрировали два разных fail-stop случая: остановка SMF против остановки UPF. В этих специально подобранных условиях **NRF-only уже различал две причины**; информационный выбор второго источника не давал преимущества простому методу.

Этап 14 впервые воспроизводит существенно более сложный отрицательный контроль:

- **SMF запущена**, UPF запущена;
- **SMF зарегистрирована в NRF**;
- **UPF слушает PFCP UDP 8805**;
- **PDU у UE не устанавливается**;
- **счётчик PFCP egress drops положителен и реальный PFCP обмен нарушен**;
- снятие ограничения восстанавливает UE PDU и наблюдаемые Session Establishment Request/Response.

Таким образом, комбинация двух **признаков наличия** (NRF-профиль и UDP socket) не определяет фактическую сервисную согласованность. Необходимы свидетельства **о взаимодействии**, а не только о существовании отдельных NF.

## 6. Критически необходимые дальнейшие исследования

1. Пассивную PFCP evidence следует связать с **конкретной PDU процедурой** по безопасной корреляции (без публикации SEID/SUPI) и проверить не только агрегатные счетчики.
2. Исследовать сценарий, где N4 не полностью заблокирован, а есть задержка или избирательная потеря конкретного PFCP типа, и отличать это от штатного восстановления.
3. Перейти от host-level privileged \`iptables\` и пакетного capture к выделенному проверяемому NF-смежному агенту, обеспечив защищённое происхождение КИЕ в **отдельном административном домене**.
4. Сравнивать активное распределение КИЕ **при одинаковой цене каждой полезной проверки**, а не считать локальный Docker oracle эквивалентом операторского диагностического API.
5. Формализовать причинно-временную согласованность \`UE outcome ↔ SMF/UPF/N4 messages ↔ NRF NFProfile\` с трёхзначным результатом: согласовано, доказано противоречие, недостаточно независимых данных.

**Реальная злонамеренная или скрытая компрометация работающей NF этим этапом не воспроизведена.** Этап обосновывает недостаточность только реестровых/сокетных КИЕ и необходимость причинно-временных свидетельств о протокольном взаимодействии.
